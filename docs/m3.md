# M3: レーンを増やす

2026-10-10。**数字は断りが無いかぎり実測**（XC7Z020 -1、125 MHz、Vivado 2024.1、Mac mini でビルド）。

## 変えたこと

- 塗り分けの語（W = K·P bit）を頂点ごとに ⌈W/64⌉ ビートで送る（入力・出力とも）。K > 4 が可能になった
- 出力のビート 2 の上位 16 bit に K を入れる（ボード側で取り違えを検出）
- 全レーンに配る信号の扇形を小さくする:
  - レーンごとにスロット o のビットを先に選び、それから OWN の 0/1 を選ぶ（`curbuf` が W 個の選択に広がらない）
  - `o` に `max_fanout = 32`
  - **読み込みの信号（書き込み許可・番地・データ）をレーンの中で1段レジスタに受ける**（K = 48 で効いた。下記）
- xsim: K = 1・2・4・8・48 で 4 ジョブ全語一致（K = 48 は 2 のべきでない・1 語 12 ビート）

## 何が先に詰まったか

1. **K = 48 で、まずタイミング**: 最初のビルドは WNS −0.224 ns（落ちた経路 682 本、Slice 92.9%）。
   最悪経路は `state` → 読み込み許可の解読 → 各レーンの LUTRAM の書き番地の選択で、遅延の 86% が配線。
   アニーリングの演算ではなく、**全レーンに配る制御信号の扇形と混雑**だった。
   読み込みの信号をレーンごとに1段受けたら +0.124 ns で通った（新しい最悪経路は温度の段の比較 → `o` の複製、論理 10 段）
2. **K = 64 で、Slice が足りない**: 配置で `The unplaced instances require 9107 slices`（空きは 7,738）。
   LUT は 1 レーン 約 880 の外挿で約 5.9 万 > 5.32 万（試算）、BRAM は約 128.5 / 140（試算）なので、**先に尽きるのは LUT（Slice）**
3. BRAM は K = 48 で 71%。NMAX = 4096 のまま（G48〜G50 の n = 3000 を載せるため）

## CPU との比較（同じアルゴリズム・ビット単位で同じ結果）

最適化した CPU 版（`sw/sa_fast.c`、別のセッションで作成。ブランチ `claude/interesting-brattain-65f077`、main には未取り込み）の実測と並べる:

| | 試行/秒 | 回路 K = 48 との比 |
|---|---:|---:|
| 回路 K = 48（125 MHz） | 6.00e9 | 1 |
| PYNQ-Z1 の Cortex-A9 × 2（sa_fast） | 1.12e8 | 回路が 54 倍速い |
| M4 Mac mini 全コア（sa_fast） | 2.98e10 | **回路が 5.0 倍遅い** |

- 試行回数は CPU と回路で同じなので、TTS99 の比もこの試行/秒の比になる
- M4 の速さはレプリカ 128 個をビットスライスにして xorshift64 を語の XOR で回したことによる。
  回路は 1 試行に 1 レーン（乱数・比較器・LUTRAM 一式）を使っていて、この形のまま M4 に並ぶには
  K ≈ 240 が要る（試算）。XC7Z020 では K = 48 が上限

## 次に考えること

- 1 レーンの LUT を減らす（レーンごとの内訳を `report_utilization -hierarchical` で見る。LUTRAM が約 270/レーン）
- クロックを上げる（K = 48 の最悪経路は温度の段の比較で、走りの経路ではない。回路だけ別クロックにする案も）
- 乱数の幅を縮める（32 bit の比較器と 64 bit の xorshift が 1 レーンの大きな部分のはず。ただし CPU 版と規則が変わる）
