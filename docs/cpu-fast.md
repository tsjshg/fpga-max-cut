# 比較相手の CPU 版を速くする（sw/sa_fast.c）

2026-10-10。回路と比べる相手として、`sw/sa.c` と**ビット単位で同じ結果**を出したまま、
同じアルゴリズムを CPU でできるだけ速く回す版を作った。
**数字は断りが無いかぎり実測**。「試算」と書いたものはクロックからの換算などで、測っていない。

## 結論

| | sa.c（未最適化） | sa_fast.c（既定のエンジン bsasg） | 倍率 |
|---|---:|---:|---:|
| M4 Mac mini・1 スレッド | 3.85e8 試行/秒 | **5.63e9** | 14.6 |
| M4 Mac mini・10 スレッド（全コア） | 2.32e9 | **2.98e10** | 12.8 |
| PYNQ-Z1 の Cortex-A9・1 スレッド | 9.78e6 | **5.56e7** | 5.7 |
| PYNQ-Z1 の Cortex-A9・2 スレッド | 1.95e7 | **1.12e8** | 5.7 |

- 回路は 1 レーンで 1.25e8 試行/秒（M1 の実測）。**A9 の 2 スレッドは回路 1 レーンとほぼ同じ**、
  **M4 の全コアは回路 1 レーンの約 240 倍**（試算: 2.98e10 / 1.25e8）。125 MHz で M4 に並ぶには、
  1 クロックに約 240 試行が要る
- 効いたのは、**塗り分けだけでなく乱数（xorshift64 の状態）もビットスライスにした**こと。
  128 レプリカの状態を「ビットごとの 128 bit の語 64 本」で持てば、xorshift64 は語の XOR 155 回になり、
  1 命令で 128 レプリカぶん進む。受け入れの判定（乱数 < しきい値）も語のまま上の桁から比べる
- 測定条件: n = 1024・d = 4 のランダム正則グラフ（`data/rr_n1024_d4_s1.adj`）、標準のスケジュール
  （`data/std_d4.sched`: T0 = 0.8・T1 = 0.2・100 段 × 10 周回）、主種 1。Mac は R = 256（1 スレッド）・
  10,240（10 スレッド）、ボードは R = 256（ref・nobr・inter4 は 16）。各 3〜5 回の最良。
  `sw/bench_fast.sh スレッド数 R 回数 [エンジン...]` でそのまま測れる
- 速さは温度で変わる（下の「温度による違い」）。回路は温度によらない

## 正しさ

- `sw/check.sh` の後半: 7 つのグラフ（d = 3・4・5・6、前の頂点とつながる循環グラフ、n = 100 のように
  64 の倍数でない n）× 2 つのスケジュール × R = 8・200（組の幅に満たない・割り切れない）で、
  **全エンジンの標準出力・`--init`・`--final` の塗り分けが sa と一致**。目標 0（初期のカット値より小さい
  目標は最初の改善で届く）も入れた。Mac と PYNQ-Z1 の両方で全部 OK（ボードは 4 分 25 秒）
- Mac とボードで、sa と sa_fast の標準出力・最後の塗り分けの md5 が一致
  （n = 1024・d = 4・R = 300・3 目標・20 段 × 5 周回）
- sa_fast も最後にカット値を数え直し、追いかけてきた値と一致することを毎回確かめる
- 照合で見つけた不具合: 語が 64 bit のエンジンで n = 100 のとき `aligned_alloc` が失敗していた
  （大きさが境界の倍数でないと NULL を返す）。直した

## 遅い理由（測って確かめたこと）

M0 では「受け入れの分岐の予測外れが大きい」と見ていた。測ると、**A9 では違い、M4 では温度しだい**だった。

### A9（PMU で直接数えた）

`sa_fast --pmu`（Linux の perf_event_open。A9 の PMU はカーネルとユーザを分けて数えられないので root で、
走っている間のカーネルの分も入る）。1 試行あたり:

| | サイクル | 命令 | IPC | 分岐の予測外れ |
|---|---:|---:|---:|---:|
| ref（sa.c と同じ書き方）・標準のスケジュール | 58.3 | 77.6 | 1.33 | 0.124 |
| ref・T = 0.2 で一定（100 周回） | 58.7 | 78.3 | 1.33 | 0.094 |
| ref・T = 2.0 で一定（100 周回） | 68.2 | 86.4 | 1.27 | 0.756 |
| nobr（受け入れを算術で）・標準 | 70.9 | 93.2 | 1.32 | 0.006 |

- 標準のスケジュールでは予測外れは 0.12 回/試行。T = 0.2 と 2.0 の差から1回あたり 14 サイクル以下（試算。
  命令の増えた分も含む）なので、1.7 サイクル/試行・3% ほど。
  **A9 の主因は命令の数**（1 試行 78 命令。64 bit の xorshift を 32 bit のレジスタ2本で回す・
  隣 4 つの番号と色を1バイトずつ読む・ループの管理）
- 分岐をなくすと予測外れはほぼ 0 になるが、命令が 20% 増えて**かえって遅い**

### M4（PMU は root が要るので、書き方を変えて比べた）

| | T = 0.2 | T = 0.8 | T = 2.0 | T = 5.0 | 標準 |
|---|---:|---:|---:|---:|---:|
| sa | 4.57e8 | 2.66e8 | 1.46e8 | 1.74e8 | 3.85e8 |
| ref | 5.99e8 | 3.35e8 | 1.83e8 | 2.14e8 | 5.09e8 |
| nobr | 6.10e8 | 6.11e8 | 6.15e8 | 6.12e8 | 6.12e8 |

（1 スレッド・R = 256・温度一定で 1000 周回）

- 分岐のある ref は温度が上がる（受け入れが五分五分に近づく）ほど遅くなり、分岐の無い nobr は温度によらない。
  **M4 では予測外れが効いていて、T = 2.0 では 3.4 倍の差**。標準のスケジュールは低温が長いので 1.2 倍
- **sa と ref の差（1.3 倍）は sa.c の `--order`・`--rng` の実行時の判定**。sa.c のこの2つを定数にしただけの
  版は 5.07e8 で ref と同じになった（結果の md5 も同じ）
- M0 の「M4 は 1 コアで約 20 サイクル」は別のスケジュール（200 周回）での値。標準のスケジュールでは
  約 11 サイクル（試算: 4.4 GHz / 3.85e8）

## 1つずつ足した効果

エンジンは `sa_fast -e 名前` で選べ、どれも結果は sa と同じ。上から順に1つずつ変えている。

| エンジン | 変えたこと | M4 1 スレッド | M4 10 スレッド | A9 1 スレッド | A9 2 スレッド | A9 サイクル/試行 | A9 命令/試行 | A9 予測外れ/試行 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| sa | （元） | 3.85e8 | 2.32e9 | 9.78e6 | 1.95e7 | | | |
| ref | 実行時の判定を外す（sa.c と同じ書き方） | 5.09e8 | 2.99e9 | 1.11e7 | 2.24e7 | 58.3 | 77.6 | 0.124 |
| nobr | 受け入れ・カット値・best の更新を算術で | 6.12e8 | 3.29e9 | 9.17e6 | 1.83e7 | 70.9 | 93.2 | 0.006 |
| inter4 | 4 レプリカを頂点ごとに交互（依存の連鎖を隠す） | 6.59e8 | 3.22e9 | 7.12e6 | 1.42e7 | 91.3 | 108.5 | 1.563 |
| word | 色を頂点ごとの語に（64 レプリカ、回路と同じ形）。ΔC と受け入れを語のビット演算で。乱数はスカラー | 1.25e9 | 7.27e9 | 1.70e7 | 3.40e7 | 38.3 | 53.0 | 0.018 |
| neon | word の xorshift64 を NEON の 64 bit × 2 レーンで | 1.73e9 | 1.04e10 | 3.98e7 | 8.02e7 | 16.3 | 13.7 | 0.030 |
| bsin | 乱数もビットスライス（128 レプリカ）。3 段のシフトを語の上で順に | 2.11e9 | 1.29e10 | 2.59e7 | 5.19e7 | 25.1 | 14.9 | 0.043 |
| bsfu | 3 段を1段にまとめる（C） | 3.55e9 | 2.00e10 | 3.27e7 | 6.54e7 | 19.9 | 11.2 | 0.018 |
| bsas | 窓をレジスタに置いて流すアセンブリ | 4.25e9 | 2.37e10 | 5.31e7 | 1.06e8 | 12.2 | 8.8 | 0.018 |
| **bsasg** | カット値の追い方もビットスライス（差 best − c の下 6 桁） | **5.63e9** | **2.98e10** | **5.56e7** | **1.12e8** | 11.7 | 7.9 | 0.003 |

各段の説明:

- **inter4** は M4 で少し効いた（1.08 倍）が、A9 では遅くなった。A9 では予測外れが 1.56 回/試行に増えている
  （gcc の出した命令の都合。原因はまだ調べていない）
- **word**（頂点ごとの語）は、隣 4 つの色を 1 語ずつ読めば 64 レプリカぶんがそろい、ΔC（同じ色の隣の数 n_same）を
  ビットごとの足し算で 64 レプリカまとめて数えられる。受け入れの印もビット演算で作って語に XOR する。
  カット値 c と best はレプリカごとに持ち、ΔC ≠ 0 で受け入れたレプリカ（標準のスケジュールで試行の 1.6%）
  だけを取り出して足す。この時点で乱数（64 回の xorshift64）が残りの大半になる
- **neon**: Mac の clang は word の xorshift のループを自動で NEON 2 レーンにしていた（word と neon が同じ速さだった）。
  効果を分けて見るため、word ではベクトル化を止めてある。A9 の gcc はしない
- **bsin〜bsas（乱数のビットスライス）**: 語 X[b] のビット i = レプリカ i の状態のビット b とすると、
  `x ^= x << 13` は「X[b] ^= X[b−13]」になり、xorshift64 の1回は語の XOR 155 回で済む（128 レプリカぶん）。
  乱数 r = 状態の上位 32 bit と、レプリカごとのしきい値 TH[n_same] を語のまま上の桁から比べる。
  しきい値が全部 0 の上位の桁は「r のその桁が 0 か」だけを見る。上から 12 桁比べてもまだ等しいレプリカが
  残っているとき（128 レプリカで 3% ほど、試算）だけ、1 桁ずつ続ける
  - bsin は 3 段を順にやるので、XOR のたびに語をメモリに書き戻す（書き込み 155 回）
  - bsfu は新しい状態の各ビットを古い状態の 2〜8 ビットの XOR で直接作る（392 項、書き込み 64 回）。
    新旧が別の配列だと `restrict` でコンパイラに伝えないと効かなかった（2.6e9 → 3.4e9）
  - bsas は b を下から順に「y_b = x_b ^ x_{b−13}、z_{b−7} = y_{b−7} ^ y_b、w_{b−7} = z_{b−7} ^ z_{b−24}」と流し、
    y の 8 語・z の 18 語の窓をレジスタに置く。C で書くとコンパイラが読み込みを前に寄せて退避が 50〜80 回出たので、
    レジスタの割り当てを生成スクリプト（`sw/gen_xs_fused.py`）で決めてインラインアセンブリにした
    （読み 115・XOR 155・書き 64）。AArch64 は q レジスタ（128 レプリカ）、ARMv7 は d レジスタ 32 本で
    前半・後半 64 レプリカずつ
- **bsasg（カット値の追い方）**: c を足し込むためにレプリカを1つずつ取り出すと、取り出す数（0〜数個）が
  毎回変わってループの出口の予測が外れる。そこで差 g = best − c ≥ 0 の**下 6 桁だけ**を語の桁で持ち、
  δ = −ΔC を語のまま足す（7 桁の繰り上がり）。下 6 桁があふれたか負になったレプリカ（数百試行に1回）だけ
  1つずつ取り出し、上の桁を増減する。上の桁が 0 で負になったら best を超えた（改善）ので、そこで best・best_t・
  目標の到達を記録する。改善は必ずここを通るので見落とさない。最後の c は best − g
  - 全部の桁（13 桁）を語で持つ版は繰り上がりの連鎖が長く、取り出す版とほとんど変わらなかった（1.0〜1.07 倍）。
    下の桁数は 4〜8 で振って 6 が最良（M4 1 スレッドで 4.93e9・5.41e9・5.67e9・5.64e9・5.48e9）

### 語の幅（乱数は bsfu の C、追い方は bsasg と同じ）

| | M4 1 スレッド | M4 10 スレッド | A9 1 スレッド | A9 サイクル/試行 |
|---|---:|---:|---:|---:|
| bs64（64 レプリカ） | 2.74e9 | 1.59e10 | 2.85e7 | 22.8 |
| bs128（128） | 4.39e9 | 2.39e10 | 3.38e7 | 19.2 |
| bs256（256） | 3.75e9 | 2.10e10 | 2.39e7 | 27.1 |

128 が最良。256 はレジスタに収まらず退避が増える。A9 の 64 は語を 32 bit のレジスタ2本で扱うので命令が多い
（31 命令/試行）。bs256 の A9 2 スレッドは R = 256 だと組が1つしかないので表から外した。

### 乱数の部分だけの速さ（128 レプリカを1回進める時間）

| | M4 | A9 |
|---|---:|---:|
| 3 段を語の上で順に（C） | 42 ns | |
| 1 段にまとめる（C、restrict） | 22.8 ns | |
| 窓を流す（C） | 18.2 ns | |
| 窓を流す（アセンブリ） | **11.5 ns**（約 50 サイクル、試算） | 1,583 サイクル（12.4 /レプリカ） |
| 同、A9 向けに並べ替え | | **1,078 サイクル（8.4 /レプリカ）** |

A9 の NEON は順にしか実行しないので、直前の結果を待つ並びがそのまま待ちになる。生成スクリプトで
「読み込みは 4 サイクル後、XOR は 3 サイクル後に使える」として、入力がそろう命令から先に出すように並べ替えた
（遅れの仮定を 1〜6 で振って、この組が最良）。それでも 1 命令 1.6 サイクルで、A9 の 1 試行 11.7 サイクルのうち
8.4 サイクルが乱数。

## 温度による違い（bsasg）

| | T = 0.2 | T = 0.8 | T = 2.0 | T = 5.0 | 標準 |
|---|---:|---:|---:|---:|---:|
| M4 1 スレッド | 6.75e9 | 3.92e9 | 2.75e9 | 2.59e9 | 5.63e9 |

（温度一定で 1000 周回、R = 256）。A9 は T = 0.2 で 13.1・T = 2.0 で 14.7 サイクル/試行（100 周回の短い走りで、
初期化の分が入る）。高温ほど遅いのは、しきい値の上位に 0 の桁が少なく比べる桁が増えるのと、差 g の下の桁の
あふれ（1つずつ直す枝）が増えるため。標準のスケジュールは低温が長いので速い側に寄る。

## ファイル

| ファイル | 中身 |
|---|---|
| `sw/sa_fast.c` | 入出力（sa.c と同じ）、エンジンの表、スレッド（組を早い者勝ちで取る。結果は割り当てによらない）、`--pmu` |
| `sw/sa_fast_grp.h` | 頂点ごとの語のエンジンの本体。語の幅・乱数の作り方・追い方・次数を決めて何度も読み込む |
| `sw/gen_xs_fused.py` → `sw/xs_fused.h` | xorshift64 のビットスライスの展開（C・AArch64・ARMv7）。展開が xorshift64 と同じかを 1000 回確かめてから書く |
| `sw/bench_fast.sh` | エンジンごとの試行/秒 |
| `sw/check.sh` | 後半に sa_fast の全エンジンと sa の照合を足した |

使い方は sa と同じ（`-e` でエンジン、既定は bsasg）。`--order rand`・`--rng sm64` は無い。
既定のエンジンは d = 3・4 を定数にした版、それ以外の d（≤ 8）は一般の版を使う。

## まだやっていないこと・見込み

- 比較（30 サイクル/頂点）は、上の 12 桁を 1 桁 4〜5 命令で比べている。しきい値の上位の 0 の桁を除くと
  実際に要る桁は 8 前後なので、もう少し削れる見込みがある（試算で 1 割前後）
- M4 の SME（512 bit のストリーミング SVE）は試していない
- A9 は乱数が 8 割。乱数の命令（1 試行 5.2 命令）を減らす形は思いついていない
- 回路側への示唆（試算）: 回路の xorshift64 は配線と XOR なので、乱数のビットスライスで CPU が得た分（命令数）は
  回路では元からかかっていない。差は「1 クロックに何試行流せるか」だけで決まる
