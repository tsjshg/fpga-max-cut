# Mac の GPU で焼きなましを回す（gpu/）

2026-10-11。「M4 の GPU でやったらすごく速いか」を確かめるため、`sw/sa.c` と**ビット単位で同じ結果**を出す
GPU（Metal の compute shader）版を作り、試行/秒と到達時間（TTS99）を測った。
**数字は断りが無いかぎり実測**。「試算」と書いたものは測っていない換算。

## 結論

| | 試行/秒（n = 1024、標準のスケジュール） | G49・6000 の TTS99 | G50・5868 | G50・5872 |
|---|---:|---:|---:|---:|
| FPGA（K = 56・125 MHz、DMA 込み） | 7.0e9 | 39.9 ms | 2.64 s | 8.08 s |
| M4 CPU 10 コア（`sw/sa_fast.c`） | 2.98e10 | **20.0 ms** | **0.69 s** | **1.99 s** |
| **M4 GPU 10 コア・エンジン a**（1 スレッド = 1 レプリカ） | 3.46e10 | 36.0 ms（R = 32） | 1.13 s（R = 2,048） | 3.72 s（R = 2,048） |
| **M4 GPU 10 コア・エンジン b**（ビットスライス） | **9.63e10** | 351 ms | 9.44 s | 11.48 s |

1. **試行/秒では GPU が勝つ。** ビットスライスのエンジン b は 100 万レプリカで 9.6e10 試行/秒、M4 CPU の 3.2 倍・FPGA の 14 倍。
   事前の試算（1e11 前後）どおり
2. **到達時間では GPU は M4 CPU に負ける**（1.6〜2.6 倍遅い）。FPGA には G50 で 2.2〜2.3 倍勝ち、易しい目標ではほぼ同じ
3. 理由は「**レプリカが少ないときの 1 本の遅さ**」。TTS99 が最小になるのは、1 回の実行で 99% に届くのに要る数
   R\* = ln 0.01 / ln(1 − p) 程度のレプリカを、効率のよい長い実行で回すときで、ここで扱う目標では R\* は 4〜2,048。
   GPU が試行/秒を出すには数万〜100 万レプリカが要り、レプリカが少ないと 1 頂点に 100〜120 ns（a）・1 µs（b）かかる。
   M4 CPU は 1,280 レプリカで 1 頂点 48 ns なので、1 回の実行が GPU の半分以下で済む
4. 試行/秒を上げるためにレプリカを増やすと、その数が R\* を大きく超えて無駄になるか、R\* を大きくするために短い実行
   （1 試行あたりの効率が悪い）を選ぶことになる。G50・5872 でエンジン b を 65,536 レプリカ・τ = 3,000 で回すと
   11.5 s で、a の 3.7 s に負ける。b が CPU に勝つのは、最も効率のよい τ でも R\* が数万を超える、ずっと難しい目標
   だけになる（試算、後述）

## 作り

ホストは Objective-C（`gpu/sa_gpu.m`）、カーネルは `gpu/sa_gpu.metal`。入出力は sa と同じ
（`.adj`・`.sched`・`-R`・`-S`・`-t`・`--init`・`--final`・`-q`、標準出力の形）。種と初期の塗り分けは CPU で sa と同じ列から作り、
32 × 32 のビット転置で GPU の形に並べ替える。最初と最後のカット値は GPU で数え直し、追いかけてきた値と突き合わせる。
長い実行は dispatch を分け（1 回はスレッドあたり約 2^20 頂点ぶん）、状態は device メモリに残す。

### エンジン a: 1 スレッド = 1 レプリカ

- SIMD グループの 32 レーン = 32 レプリカが、同じ頂点を同時に処理する（頂点は順に回すので、どのレプリカも試行 t の頂点は同じ）
- 頂点ごとの 32 bit の語（ビット lane = レーン lane のレプリカの色）を SIMD グループで共有する。隣の語は全レーンが同じ番地を読む
- 乱数はレーンごとの xorshift64（32 bit の 2 語で、1 試行 18 命令）。受け入れを `simd_ballot` で語にし、全レーンが同じ値を書き戻す
- 語の置き場は 2 通り: threadgroup メモリ（1 SIMD グループ 4n バイト）か device メモリのまま（キャッシュ任せ）。
  threadgroup メモリは 1 コア 32 KB なので、n = 3000（12 KB）だと 1 コアに 2 本しか載らず待ちが隠せない。
  **n > 2048 では device メモリを使う**（G50 で 1.55e10 → 3.33e10 試行/秒）
- レプリカが少ないとき（R ≤ 2048）は、隣の番号を 2 頂点先・語を 1 頂点先に読んでおく（次の頂点の隣に今の頂点があれば、
  書き戻した値に直す）。1 回の実行が 14〜18% 縮む。レプリカが多いと命令が増えるぶん 8% 遅いので使わない

### エンジン b: ビットスライス（sa_fast の bsasg と同じ考え）

- 1 スレッドが 32 レプリカを持つ。頂点ごとの語は device メモリに `[頂点][スレッド]` で並べる（SIMD グループの 32 スレッドが
  128 バイトの連続した番地を読む）
- xorshift64 の状態を「ビットごとの 32 bit の語 64 本」でレジスタに持ち、1 回は語の XOR 155 回（32 レプリカぶん）
- `r < TH[ns]` は語のまま上の桁から比べる。どのしきい値でも 0 の上の z 桁は「r のその桁が全部 0 か」の OR をまとめてとり、
  残りの桁はどのレプリカも決まったら飛ばす。z は段ごとに一様なので、展開した列の途中へ `switch` で飛び込む
- カット値は差 g = best − c の下 4 桁をビットスライスで足し込み、桁あふれだけレプリカごとに直す（上の桁は device メモリ）

### 正しさ

- `gpu/check.sh`: 7 つのグラフ（d = 3・4・5・6、循環グラフ、64 の倍数でない n）× 2 つのスケジュール × R = 8・200・1000 の
  42 件を、エンジン a・b の 8 通りの設定（既定、先読みなし、語を device メモリに、dispatch を段の途中で細かく分ける・
  threadgroup を小さく、g の下の桁を 3、g を全部の桁で）で走らせ、**標準出力・`--init`・`--final` の塗り分けが sa と全部一致**
- 到達時間の測定の 43 回の実行（G50・10 万周回の 64 レプリカ（a）と 1,024 レプリカ（b、313 秒）を含む）すべてで、
  **先頭のレプリカ（最大 10,240）の best と目標の到達時刻が、M4 の `sa_fast` の実行（data/m4/m4.json）と一致**
- 照合で見つけた不具合: d = 5・6 で g の下の桁を 2 にすると壊れる（δ = −d..d が下の桁 + 1 桁に収まらない）。
  2^GL ≥ d をホストで確かめるようにした

## 何で律速しているか

### エンジン b（部分を外した版で切り分け。結果は正しくない、速さだけ見る）

rr1024・標準のスケジュール（1,000 周回）・R = 262,144:

| 外したもの | 時間 | 試行/秒 |
|---|---:|---:|
| なし | 3.13 s | 8.6e10 |
| 乱数 | 2.07 s | 1.3e11 |
| 比較 | 2.58 s | 1.0e11 |
| カット値の追跡の桁あふれの直し | 2.82 s | 9.5e10 |
| カット値の追跡 | 2.79 s | 9.6e10 |
| 比較と追跡 | 1.67 s | 1.6e11 |
| 比較と追跡と乱数 | 1.66 s | 1.6e11 |

- 比較と追跡を外すと、乱数を外しても変わらない（1.67 s → 1.66 s）。このとき律速しているのは塗り分けの読み書きで、
  1 頂点 5 語の読みと 1 語の書き × 8,192 スレッド × 1,000 周回 × 1,024 頂点 = 2.0e11 バイトを 1.66 s、
  **約 120 GB/s で M4 のメモリ帯域（120 GB/s）とほぼ同じ**（試算）。26 万レプリカの塗り分けは 32 MB でキャッシュに収まらない
- 演算は乱数 155 XOR・比較・追跡で 1 頂点（32 レプリカ）あたり 300〜400 命令。ビットスライスの xorshift だけなら単体で
  26 万スレッド 8.65e9 回/秒（1.34e12 XOR/秒）出る
- **GPU では「まれな枝」が安くない。** 1 本の SIMD グループは 32 スレッド × 32 レプリカ = 1,024 レプリカを足並みをそろえて
  動かすので、どれか 1 つでも桁あふれや改善があれば全員がその枝を通る。CPU（sa_fast）では「数百試行に 1 回」で済んだ
  桁あふれの直しが、GPU ではほぼ毎回走る（上の表で 1 割）

### エンジン a

- 1 試行あたり約 50 命令（乱数 18・隣 4 つを数える 16〜20・判定・ballot・ループ）。26 万レプリカで 3.46e10 試行/秒は、
  1.58e12 演算/秒（実測の上限）÷ 50 ≈ 3.2e10 とほぼ同じで、**演算で律速**している
- 乱数を外しても 2 割しか速くならず（7.76 s → 6.13 s）、ビットスライスの b ほど乱数が重くない分、隣を数えて受け入れを作る
  部分がそのまま 32 倍の命令になる

### レプリカが少ないとき（TTS で効く）

- a の 1 頂点 約 100〜120 ns は、命令の数ではなく**1 本の SIMD グループの命令の待ち**で決まる。SIMD グループは命令を順にしか
  出さないので、「隣の番号を読む（46 ns）→ 隣の語を読む（46 ns）→ 数えて判定（依存 8 段 × 2.6 ns）→ ballot → 書き戻し」が
  そのまま積み重なる。threadgroup メモリ・ballot・乱数をすべて外しても 1 頂点 116 ns 残った（R = 1,024）。
  先読みで 120 → 100 ns 程度までは縮んだが、それ以上は縮まなかった
- b の 1 頂点 約 1 µs も同じで、1 頂点に 300〜400 命令の依存の長い列（比較の桁の連鎖、足し算の繰り上がり）を
  1 本の SIMD グループが順に流す
- 短い実行（数十 ms）は 1 回目が遅く、続けて走らせると速くなる（G48・τ = 100・64 レプリカで 57 → 47 → 42 → 39 → 36 ms）。
  GPU の周波数が上がるまでの立ち上がりと見ている（周波数そのものは測っていない）

## 到達時間（TTS99）

`gpu/bench_tts.py`・`gpu/tts_report.py`。docs/m4.md と同じ式・同じ問題・同じスケジュール（`data/m4/*.sched`）。
p は M4 の 10,240 レプリカの値（`data/m4/m4.json`）をそのまま使う（同じ探索をするので、アルゴリズムの性質）。
FPGA と M4 CPU の数字は docs/m4.md と同じもの（FPGA は 896 レプリカで固定、M4 は 1,280 レプリカ）。

GPU はエンジン・レプリカ数 R・τ を選べるので、(1) 100 段 × 3 周回の短い実行で (エンジン, R) ごとの 1 回の時間を測り、
τ に比例するとして TTS99 を見積もる（試算）、(2) 目標・τ・エンジンごとに見積もりが最小の R で実際のスケジュールを走らせる（実測）、
(3) 実測の時間で TTS99 を出して最良を選ぶ、とした。R の候補は a が 32〜65,536、b が 1,024〜262,144（2 の累乗など）。

### わかったこと

1. **TTS99 を決めるのは、R\* 程度のレプリカで回したときの 1 回の実行の時間。** p が小さい目標ほど長い τ のほうが 1 試行あたりの
   効率がよく（G50・5872 で τ = 3,000 は 4.2e11 試行、10 万周回は 1.1e10 試行）、長い τ では R\* が小さい（36〜2,048）。
   R\* 個を同時に走らせ、その 1 回が短い機械が勝つ
2. **GPU はレプリカが少ないと遅い。** a は 2,048 レプリカまで 1 頂点 約 100〜125 ns で、FPGA（896 レプリカで 128 ns）とほぼ同じ。
   M4 CPU（1,280 レプリカで 48 ns）の 2〜2.6 倍。だから G50 では「FPGA と同じ速さで、FPGA の 2.3 倍のレプリカを一度に回せる」ぶん
   FPGA に勝ち（R\* = 2,048 を 1 回で済ませる。FPGA は 896 で 2.3 回）、M4 CPU には 1 回の短さで負ける
3. **エンジン b（試行/秒は 3 倍）が効く場面はここには無い。** b は 32,768 レプリカまで 1 頂点 1 µs で、数十万レプリカに
   しないと速さが出ない。G50・5872 で R\* が 47,155 になる τ = 3,000 を選んでも、その τ は効率が悪く 11.5 s かかる
4. **b が M4 CPU に勝つ条件（試算）。** R\* ≫ R のとき TTS99 ≈（1 レプリカあたりの TTS99 の試行回数）÷（試行/秒）なので、
   最も効率のよい τ での R\* が、b がその数で M4 CPU（2.9e10）を超える数 ≈ 3 万以上なら b が勝つ。G50・5872 の
   10 万周回で R\* = 36、最良既知の 5880 でも 10 万周回・1,024 レプリカで 1 つ届いた（docs/m4.md）程度なので R\* は数千で、
   ここで扱える目標はどれもその手前。GPU の試行/秒を活かせるのは、もっと大きなグラフか、もっと届きにくい目標になる
5. GPU の「試行/秒」と「到達時間」の差は、FPGA で見た「易しい目標では 1 回の短さで決まる」（docs/m4.md）がさらに強く出たもの。
   GPU は 1 本が遅いぶんを数で補う機械なので、数が要らない問題では速さが出ない

## 言えないこと・まだやっていないこと

- GPU の走っている間の周波数は測っていない（`sudo powermetrics --samplers gpu_power` で見られるが root が要る）。
  短い実行の 1 回目が遅いのは周波数の立ち上がりと見ているが、確かめていない
- p は 10,240 レプリカでの推定（docs/m4.md と同じ）。G50・5872 の τ = 3,000 は 1 つしか届いておらず、その行は誤差が大きい
- τ は M4・FPGA と同じ候補（G49 は 100 以上）だけ。易しい目標はもっと短い τ のほうがどの機械も速いはず
- エンジン b の塗り分けを threadgroup メモリに置く形（1 SIMD グループ 1,024 レプリカで n·128 バイト、n = 1024 で 128 KB）は
  収まらないので試していない。帯域の律速を外すには、n が小さい問題か、レプリカの持ち方を変える必要がある
- 電力あたりの比較はまだ（電力計の入手待ち）
