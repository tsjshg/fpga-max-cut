# PYNQ-Z1 の焼きなましで Max-Cut を解く

[English](README.md)

小さな FPGA で、**重みなし Max-Cut** の焼きなましをどこまで速くできるかを試すプロジェクトです。焼きなましの探索エンジンを **PYNQ-Z1**（Zynq XC7Z020）の上に Verilog で自作し、**同じアルゴリズムを同じだけ手をかけて速くした CPU 版**と比べています。CPU はボード上の Cortex-A9 と、Apple M4 の Mac mini です。

目指すのは「よい解を速く得る」ことで、最適性の証明は扱いません。「FPGA なら速い」を前提にせず、速さ・解の質・資源量を分けて測り、勝っても負けてもそのまま書きます。

**解説ページ: <https://tsjshg.github.io/fpga-max-cut/>。** 最大カット問題とは何か、解き方、焼きなまし法、回路にした方法を、図を付けて英語と日本語で説明しています。

## ここまでの結果

ランダム 4 正則グラフ（n = 1024、辺 2048 本）で、1 回あたり 1000 周回。数字はすべて**実測**です。

| エンジン | レプリカ | 試行/秒 | FPGA との比 |
|---|---:|---:|---|
| **FPGA**（56 レーン・125 MHz） | 896 | **7.0 × 10⁹** | — |
| 同じボードの Cortex-A9 × 2（`sw/sa_fast.c`・2 スレッド） | 256 | 1.12 × 10⁸ | FPGA が **63 倍速い** |
| Apple M4 Mac mini・10 コア（`sw/sa_fast.c`） | 10,240 | 2.98 × 10¹⁰ | FPGA が **4.3 倍遅い** |

- **どのエンジンもまったく同じ道筋で探索します。** 同じ種を与えると、FPGA・CPU の正解版（`sw/sa.c`）・最適化した CPU 版は、ビット単位で同じ結果を出します。ボードの出力も、全部の語を CPU と照合しています。そのため、目標のカット値に届くまでの試行回数はどこでも同じで、到達時間の比は試行/秒の比になります。
- このグラフで見つかった最良のカット値は 1774 です。最適であることの証明はありません。
- **M4 が勝つ理由。** 最適化した CPU 版は 128 レプリカをビットスライスにして持つので、128 bit の XOR 1回で xorshift64 を 128 個ぶん進めます。FPGA は 1 クロック 1 試行に 1 レーンあたり約 450 LUT を使い、XC7Z020（28 nm・2012 年）は 56 レーンで Slice の 90% を使います。M4（3 nm・2024 年）に 125 MHz で並ぶには約 240 レーンが要ります（試算）。
- **電力あたりの比較はまだ測っていません。** ボードは数 W、Mac mini は負荷時に数十 W なので、そちらでは結果が変わるかもしれません。

## しくみ

**アルゴリズム。** d 正則グラフの上で、1 頂点ずつ反転する Metropolis 法の焼きなましです。頂点は決まった順に回します。ランダムに選ぶより、到達時間で約 4 倍良かったためです（実測）。使うのは整数だけです。

- レプリカごとに xorshift64 の乱数を持ち、1 試行に必ず 1 回進めます。
- 頂点 v を反転するとカット値は ΔC = 2·n_same − d だけ変わります（n_same は同じ色の隣の数）。ΔC ≥ 0 か、r < TH[n_same] なら受け入れます。
- しきい値の表 TH = ⌊exp(ΔC/T)·2³²⌋ は、ホストで**1回だけ**計算して（`sw/make_sched.py`）整数のまま全エンジンに渡します。浮動小数を使うのはここだけで、そのおかげで Mac・Cortex-A9・FPGA の結果がビット単位で一致します。

**回路**（[`hw/rtl/`](hw/rtl/)、詳しくは [`docs/m1-design.md`](docs/m1-design.md)）:

```
          1 窓 = 16 クロック。全レプリカが同じ頂点 v を処理する
 レーン 0:  レプリカ 0  1  2 ... 15 | 0  1  2 ... 15 | ...   5 段のパイプライン、
 レーン 1:  レプリカ 16 17 ...   31 | 16 17 ...   31 | ...   1 レーン 1 クロック 1 試行
  ...                                                       （16 レプリカを交互に流すので
 レーン K-1                                                   読み書きの衝突が起きない）
            |<----- 頂点 v ----->|<--- 頂点 v+1 --->|

 塗り分けは BRAM に、頂点ごとに (16·K) bit の語で持つ（ビット p = レプリカ p の色）
 頂点 v の窓の間に、v+1 の隣の語を先読みする。
 隣が v 自身（まだ書き換え中）のときは、BRAM でなくレジスタから取る
```

- 1 レーンに 16 レプリカを交互に流すので、同じレプリカの次の試行は 16 クロック後です。読み書きの衝突は、形のうえで起きません。
- K 本のレーンは足並みをそろえて同じ頂点を処理します。16·K レプリカぶんの塗り分けを頂点ごとに 1 語で持つので、BRAM の口 1 つで全レーンに足り、BRAM が律速になりません。
- 動いている間は、すべてオンチップのメモリで回ります。AXI DMA のストリーム 1 本でジョブを入れ、1 本で結果を返します。結果は、最良のカット値、それが出た試行番号、目標に初めて届いた試行番号、最後のカット値、最後の塗り分けです。
- 速さは回路の中のサイクルカウンタで測ります。値は常にちょうど (窓の数 + 1) × 16 です。

**XC7Z020 に何本入るか**（125 MHz、資源は DMA なども含む全体、すべて実測。[`docs/m3.md`](docs/m3.md)）。最後の 2 行は、1 レーンの LUTRAM を詰めた後の版です（試行番号を 32 bit に、結果を書き口から読む）。1 レーンが約 600 から約 450 LUT になりました:

| レーン K | レプリカ | WNS (ns) | LUT | BRAM タイル | ボードでの試行/秒 |
|---:|---:|---:|---:|---:|---:|
| 1 | 16 | +0.196 | 6,172 (12%) | 16.5 | 1.25 × 10⁸ |
| 8 | 128 | +0.294 | 11,352 | 29 | 1.00 × 10⁹ |
| 16 | 256 | +0.070 | 17,318 | 43 | 2.00 × 10⁹ |
| 32 | 512 | +0.285 | 31,395 (59%) | 71.5 | 4.00 × 10⁹ |
| 48 | 768 | +0.124 | 44,652 (84%) | 100 (71%) | 6.00 × 10⁹ |
| 64 | 1,024 | Slice が足りず配置に失敗 | | | |
| 48・詰めた後 | 768 | +0.167 | 35,235 (66%) | 100 | 6.00 × 10⁹ |
| **56・詰めた後** | **896** | **+0.135** | **40,490 (76%)** | **114.5 (82%)** | **7.00 × 10⁹** |

142.86 MHz は通りませんでした（WNS −0.09〜−0.44 ns。56 レーンでは AXI DMA の中が最悪経路）。そのため 125 MHz のままです。

## 検証

- CPU の正解版 `sw/sa.c` は、別の書き方をした Python 版（`sw/sa_check.py`）と突き合わせています。Mac と Cortex-A9 で出力が一致します。
- **xsim**: K = 1・2・4・8・48・56 レーンで 4 ジョブを続けて流し、入力にはランダムな途切れを、出力には背圧をかけています。出力の全語が CPU の正解と一致します。わざと壊した版はちゃんと FAIL になります（FWD を切る、書き戻しを 1 クロック遅らせる、先読みの受け取りを 1 クロック早める）。
- **ボード**: K = 1・2・4・8・16・32・48・56 で、出力の全語が一致します。期待値は、ボードの上で CPU の正解版がその場で作ります。

## ファイル構成

```
sw/sa.c              CPU の正解版。回路はこれとビット単位で一致しなければならない
sw/sa_fast.c         比較用に最適化した CPU 版（レプリカをビットスライス）。結果は sa.c と同じ
sw/gen_regular.py    ランダム d 正則グラフ（試験用の循環グラフも）
sw/make_sched.py     温度スケジュール → 整数のしきい値の表（.sched）
sw/job.py            ストリームの形: 入れるジョブと、返るはずの結果（xsim とボードで共通）
sw/mkvec.py          CPU の正解版から xsim の照合ベクタを作る
sw/check.sh          CPU 側の照合（sa と sa_check.py、sa_fast と sa）
hw/rtl/              mc_core.v（読み込み・窓の制御・出力）、mc_lane.v（パイプライン 1 本）
hw/sim/              途切れと背圧をかけるテストベンチ。run.sh <K>
hw/build.tcl         PS7 + AXI DMA + mc_core。引数: bd|all [FCLK MHz] [K] [並列数]
host/mc.py           ボード上で: ジョブを流し、全語を CPU と照合し、試行/秒を出す
data/                固定の試験用グラフと標準のスケジュール
docs/                設計メモと測定の記録（日本語）
```

## 自分で試すには

PYNQ v3.1 のイメージを入れた PYNQ-Z1 と、Vivado 2024.1 が要ります。Mac から Vivado を動かす道具（Docker の中で、または Linux のビルド用マシンで）、ボードの準備、ボードへの送り方は **[fpga-mac](https://github.com/tsjshg/fpga-mac)** にあるので、先にそちらを整えてください。このリポジトリは fpga-mac の PYNQ-Z1 のひな形から始めています。下の `vivado.sh` と `pynq.sh` は fpga-mac のスクリプトです。

ビルド済みのビットストリームは、まだ同梱していません。

**1. CPU 側**（C コンパイラと Python 3 があればどの Unix でも。numpy はボードでだけ使います）

```bash
make -C sw
sw/check.sh                       # sa と Python 版、sa_fast と sa の照合
sw/sa -g data/rr_n1024_d4_s1.adj -s data/std_d4.sched -R 256 -j 8 -t 1774 -q
sw/sa_fast -g data/rr_n1024_d4_s1.adj -s data/std_d4.sched -R 1024 -j 8 -t 1774 -q
```

**2. シミュレーション**（ベクタは Mac で作り、シミュレーションは Vivado のある場所で走ります）

```bash
python3 sw/mkvec.py --K 1
cd hw
vivado.sh sh 'sim/run.sh 1'       # → PASS: K=1, 4 jobs, ... all match
```

**3. ビットストリーム**

```bash
vivado.sh build build.tcl bd 125 56 2     # 先にブロックデザインの検証（30 秒ほど）
vivado.sh build build.tcl all 125 56 2    # → out/mc125_k56.bit と .hwh
```

最後の引数は Vivado の並列数です。メモリ 15 GB の Docker なら 2、大きな Linux のビルド用マシンならもっと増やせます。

**4. ボードで。** `sw/` を `~/<dir>/sw` に置いて、そこで `make` します。続けて、`host/*` と `sw/job.py` と `.bit`/`.hwh` を `~/<dir>/host` に、`data/*` を `~/<dir>/data` に置きます。

```bash
pynq.sh run <dir>/host mc.py mc125_k56.bit ../data/rr_n1024_d4_s1.adj ../data/std_d4.sched --K 56 --target 1774
```

全語が CPU と一致したか、サイクル数、試行/秒が出ます。896 レプリカぶんの期待値を、ボードの CPU 版が作るのに 50 秒ほどかかります。
